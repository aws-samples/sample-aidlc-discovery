# Contributing Guidelines

Thank you for your interest in contributing to `aidlc-discovery`. Whether it's a bug report, a new interview question, a correction, or a documentation improvement, we value feedback and contributions from the community.

Please read through this document before submitting any issues or pull requests.

## What this project is

`aidlc-discovery` is a role-based interview workflow that produces the two canonical inputs AI-DLC needs before Inception: a Vision Document and a Technical Environment Document, plus a handoff file of pre-declared open questions. It is a companion tool to [AI-DLC](https://github.com/awslabs/aidlc-workflows), not a fork.

See [README.md](README.md) for the design principles this project is built on.

## Contributing rules

The rule set lives in `aidlc-discovery-rules/aidlc-discovery-rule-details/`. When contributing:

- **Be reproducible.** Changes should be consistently reproducible either via test case or a documented set of steps.
- **Single source of truth.** Don't duplicate content. If guidance applies to both roles, put it in `common/` or `shared/` and reference it.
- **Keep it agnostic.** The core methodology shouldn't assume specific IDEs, agents, or models. Natural-language triggers and the markdown-with-`[Answer]:` question format are the contract; IDE wrappers are generated by the installer.
- **User-facing content in the user's language; control content in English.** See `common/language-handling.md` for the split — do not move identifiers, file names, or state metadata out of English.

### Directory structure — do not rename or move

The folder names under `aidlc-discovery-rules/` are part of the public contract. The installer, the `release.yml` workflow, and the core-workflow path-resolution logic all depend on these exact names. Do not flatten, rename, or reorganize them.

```text
aidlc-discovery-rules/
├── aidlc-discovery-core-workflow.md           # Entry point
└── aidlc-discovery-rule-details/
    ├── common/                             # Cross-role guidance
    ├── shared/                             # Project-type + open-questions collector
    ├── business/                           # Vision interview + completion gate
    └── technical/                          # Technical Environment interview + completion gate
```

### Rule structure

Rules are organized by responsibility:

- `common/` — shared guidance across both roles (welcome, session continuity, role selection, question format, content validation, audit format, language handling).
- `shared/` — stages used by both roles (project-type selection, open-questions collector).
- `business/` — the Vision Document interview and its completion gate.
- `technical/` — the Technical Environment Document interview and its completion gate.

### Testing changes

Before submitting a PR, test your rule change end-to-end with at least one supported platform (Claude Code, Kiro, Cursor, Cline, or Amazon Q Developer). Describe in the PR:

- Which rule files you changed and why.
- Which platform you tested on.
- A short recorded session showing the new behaviour (a terminal transcript or a gif is ideal).

If you're adding or updating installation instructions in `install.md`, ensure you've tested them on macOS, Windows PowerShell, and Windows CMD. The install pattern is shell-based and regresses easily on Windows.

## Reporting bugs / feature requests

Use GitHub issues to report bugs or suggest features. Before filing, check existing issues to avoid duplicates.

Please include:

- Which stage or question is affected (`Q5`, `T14`, `Section 3`, the completion gate, etc.).
- The IDE and agent you tested with.
- Expected vs actual behaviour.
- A minimal reproduction: the workspace state, the prompt you used, and the output the tool produced.

## Contributing via pull requests

### Start with an issue

We encourage opening an issue before working on a PR. It helps us and the community understand what you have in mind, discuss the approach, and align on scope before you invest time. For small fixes like typos or lint corrections, feel free to go straight to a PR.

### AI-generated contributions

PRs produced by AI coding agents are welcome and follow the same process. Start with an issue, align on scope, and meet the quality bar.

### Submitting your PR

1. Work against the latest `main` branch.
2. Check existing open and recently merged PRs.
3. Fork the repository.
4. Make your changes (keep them focused — one concern per PR).
5. Update [CHANGELOG.md](CHANGELOG.md) under `[Unreleased]` with a brief note of the change (Added / Changed / Fixed / Removed).
6. Use clear commit messages following [conventional commits](https://www.conventionalcommits.org/) (e.g., `feat:`, `fix:`, `docs:`).
7. Submit the PR and respond to feedback.

### PR closure

We review every PR and want to help contributions land. To maintain project quality, we may close PRs that are out of scope or don't follow the guidelines described here. If that happens, you're always welcome to open an issue and try again.

## Relationship to AI-DLC

`aidlc-discovery` is designed to live alongside [AI-DLC](https://github.com/awslabs/aidlc-workflows). Its output (`Product-Definition/vision-document.md`, `Product-Definition/technical-environment.md`, `Product-Definition/open-questions.md`) is the direct input to AI-DLC's Inception phase. When contributing:

- Preserve that handoff contract. Do not rename or restructure the three output files without a migration plan for AI-DLC consumers.
- If AI-DLC changes its expectations for Vision or Technical Environment inputs, open an issue proposing the corresponding update to `aidlc-discovery` — we track drift against AI-DLC as a first-class concern.
